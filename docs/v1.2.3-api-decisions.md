# RESERVE v1.2.3 API Decision Register

This is the active decision register for the v1.2.3 Workflows API evolution.
The authentication design is documented in
[`reserve-workflows-api/API-AUTHENTICATION.md`](../reserve-workflows-api/API-AUTHENTICATION.md).

The goal is to resolve these decisions before implementation begins so the
CLI, Cloudflare Worker, email service, and storage model share one contract.

## Decision summary

| Area | Proposed direction | Status |
|---|---|---|
| Public browse access | Keep public read-only catalog and workflow discovery available without a RESERVE token. | Proposed |
| FRED API key | Validate once during enrollment; never use it as a RESERVE bearer token and never store the raw key in RESERVE services. | Proposed |
| FRED fingerprint | Store a one-way fingerprint only if needed for identity linkage, duplicate detection, or abuse controls; define retention and deletion rules. | Open |
| Identity | Use a verified email as the RESERVE identity, subject to explicit account-linking and recovery rules. | Proposed |
| RESERVE credential | Issue an independent opaque, cryptographically random bearer token; store only a server-side hash. | Proposed |
| Token lifetime | Choose expiration, rotation, revocation, multi-device behavior, and recovery semantics before implementation. | Open |
| CLI secret storage | Use the native OS credential store where available, with a documented restrictive-file fallback. | Proposed |
| Enrollment email | Use the Cloudflare-compatible email delivery path with short-lived, single-use verification challenges. | Open |
| Authorization | Separate authentication from access to public, private, repository-scoped, and publishing operations. | Open |
| Bootstrap migration | Define how the temporary `RESERVE_API_KEY` mechanism is retired or retained for operations. | Open |

## Decisions required before coding

### 1. Public versus authenticated routes

Decide which routes remain public. The recommended first boundary is:

- public: health, public catalog browse, public collection metadata, and public
  workflow retrieval;
- authenticated: account status, enrollment completion, private repositories,
  publishing, and any user-specific operations.

The API must document whether a valid token is optional on public routes or
whether public and authenticated variants have different response behavior.

### 2. FRED-key validation

Decide the exact FRED endpoint used for validation, the minimum request scope,
timeout and retry behavior, and whether validation happens only at enrollment
or can be repeated later. The raw FRED key must remain in the CLI-to-service
request path only as long as required for validation and must not be logged,
persisted, or returned.

Also decide whether a FRED fingerprint is necessary at all. If retained, define
whether it is used for duplicate-account prevention, abuse detection, account
recovery, or only audit purposes.

### 3. Email identity and account linking

Define email normalization, case handling, resend behavior, expiration,
single-use semantics, and what happens when a verified email is paired with a
different FRED key. Decide whether one email may own multiple identities and
whether a user can replace or remove the FRED association later.

### 4. Token lifecycle

Choose opaque token length and prefix, access-token lifetime, rotation behavior,
revocation granularity, maximum active tokens per identity, device labeling,
lost-token recovery, and whether refresh tokens are necessary. The initial
implementation should avoid refresh tokens unless the user experience requires
long-lived sessions that cannot be handled by explicit rotation.

### 5. CLI credential storage

Specify the credential-store interface and platform behavior for macOS Keychain,
Linux Secret Service or an equivalent, Windows Credential Manager, headless
systems, and restrictive-file fallback. Define how `status`, `logout`, `revoke`,
and `rotate` behave when the local credential is missing or the service is
unavailable.

### 6. Authorization model

Define scopes or roles for public reads, private repository reads, publishing,
administration, and future organization membership. A valid enrollment token
should not implicitly authorize publishing or private repository access.

### 7. Rate limits and abuse controls

Set limits for registration, verification resend, verification attempts, FRED
validation, login, token rotation, and public catalog reads. Decide which limits
are keyed by IP, email, FRED fingerprint, token, or a combination, and define
the public error and retry contract.

### 8. Cloudflare data model and retention

Choose the storage product, account/region boundary, encryption responsibilities,
retention period, deletion workflow, audit-event retention, and backup behavior.
Document which values are hashes, which are personal data, and which may be
returned to the CLI.

### 9. Bootstrap and rollout

Decide how the current temporary `RESERVE_API_KEY` bootstrap is used during the
transition, whether it remains available for service-to-service operations,
and how it is rotated or retired. Define staging versus production enrollment,
email delivery, storage, and token namespaces before enabling public enrollment.

### 10. Failure, privacy, and support behavior

Define uniform responses that prevent account enumeration, user-visible error
messages that do not expose secrets, support procedures for lost credentials,
data deletion requests, and the minimum audit trail needed to investigate abuse.

## Exit criteria for the authentication design

Implementation should not begin until the project has agreed on:

- the public/authenticated route matrix;
- the exact FRED validation request and raw-key handling boundary;
- identity-linking and fingerprint retention behavior;
- token lifecycle and CLI storage behavior;
- authorization scopes and bootstrap migration;
- Cloudflare storage, rate limits, retention, and rollout controls.
